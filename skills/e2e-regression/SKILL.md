# e2e-regression

변경된 코드가 영향을 주는 화면을 찾아, 그 화면들의 **모든 사용자 동작**을 실제 브라우저로 조작해 보고 깨진 곳을 보고한다. 사용자가 매번 "이걸 테스트해라"고 지시하는 비용을 없애는 게 목적이므로, 대상 선정부터 판정까지 스스로 끝낸다. 진행 중 사용자에게 묻는 건 아래 "멈추고 묻는 경우"뿐이다.

결과물은 리포트 하나. 테스트 코드·spec 파일은 만들지 않고 프로젝트에 흔적도 남기지 않는다.

## 인자

| 인자 | 범위 |
|---|---|
| (없음) | 기본 브랜치와의 merge-base 이후 커밋 + 커밋 안 된 변경(staged/unstaged/untracked) |
| `<브랜치>` / `<커밋>` | 그 지점 이후 ~ 현재 작업 트리 |
| `A..B` | 해당 커밋 범위만 |
| `all` | diff 무시, 앱의 모든 라우트 전수검사 |

기본 브랜치: `git symbolic-ref --short refs/remotes/origin/HEAD` (없으면 `main`, 그다음 `master`).

## 1. 대상 화면 선정

### diff 모드

1. `git diff --name-only <base>` + `git ls-files --others --exclude-standard`로 변경 파일 수집. 테스트·문서·설정 파일 등 런타임 UI와 무관한 건 제외하되, 공용 설정(라우터, 전역 스타일, API 클라이언트, 상태 store)은 영향이 넓으니 포함.
2. 각 변경 파일에서 **위로 추적**: 그 파일을 import하는 곳을 grep으로 따라 올라가 라우트(페이지) 진입점까지 도달. 라우트 정의는 프레임워크별로 다르다 — Next.js `app/**/page.*`·`pages/**`, React Router 설정, Vue Router `routes`, SvelteKit `routes/**/+page.*`, Nuxt `pages/**` 등. 실제 프로젝트 구조를 보고 판단.
3. `git diff <base> -- <file>`로 **무엇이 바뀌었는지** 읽는다. 바뀐 핸들러·조건부 렌더링·폼 검증·API 호출이 곧 집중 검증 대상이다.
4. 공용 컴포넌트처럼 영향 화면이 많으면 전부 포함하되, 화면마다 그 컴포넌트를 쓰는 지점을 우선 검증.

### all 모드

라우트 정의를 전부 수집해 화면 목록을 만든다. 동적 라우트(`/items/[id]`)는 목록 화면에서 실제 항목을 클릭해 진입한다(임의 id 추측 금지 — 404를 버그로 오판한다). 화면 수가 많으면 핵심 흐름(인증·주요 CRUD·결제/제출) 먼저, 정적 페이지는 뒤로.

### 테스트 계획 출력

선정 결과를 짧게 출력하고 **승인을 기다리지 말고 바로 진행**한다:

```
대상: 4개 화면 (diff: main...HEAD + 작업 트리, 변경 파일 7개)
- /cart        ← src/features/cart/CartItem.tsx (수량 변경 로직)
- /checkout    ← src/features/cart/useCart.ts
...
```

## 2. 환경 준비

1. **패키지 매니저**: lockfile로 판단(`pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `bun.lock*` → bun, 그 외 npm). `node_modules`가 없거나 lockfile보다 오래됐으면 install.
2. **playwright-cli**: `playwright-cli --version`이 실패하면 `npm i -g @playwright/cli@latest`. 프로젝트 package.json은 건드리지 않는다(1회성 진단이므로). 브라우저 실행이 실패하면 `playwright-cli install-browser`.
3. **실행 폴더**: playwright-cli는 스냅샷·로그를 현재 디렉터리의 `.playwright-cli/`에 쓴다. 프로젝트를 더럽히지 않도록 OS 임시 폴더에 실행 폴더를 만들고(`RUN_DIR=$(mktemp -d)`), **모든 playwright-cli 명령은 `cd "$RUN_DIR" && playwright-cli ...` 형태로** 실행한다. 업로드 파일 등 경로 인자는 절대경로로.
4. **dev 서버**: package.json의 `dev`(없으면 `start`/`serve`) 스크립트와 포트를 확인. 그 포트가 이미 응답하면 그대로 쓰고, 아니면 백그라운드로 띄운 뒤 응답할 때까지 대기. **직접 띄운 경우에만** 끝나고 종료한다. 서버 로그에 컴파일 에러가 있으면 브라우저 진단 전에 그것부터 보고.
5. **로그인**: 대상 화면이 인증을 요구하면 `.env*`, `README`, seed 스크립트에서 테스트 계정을 찾아(`E2E_`, `TEST_USER`, `SEED_` 등) 로그인 화면으로 한 번 로그인하고 `state-save "$RUN_DIR/auth.json"`. 이후 세션이 끊기면 `state-load`. 계정을 못 찾으면 멈추고 묻는다.

## 3. 진단 실행

화면마다:

1. `goto` → `snapshot`으로 화면의 인터랙티브 요소 전수 파악(버튼, 링크, 입력, 셀렉트, 체크박스, 탭, 모달 트리거, 드롭다운 메뉴 등).
2. **모든 동작을 시나리오로 수행**. 깊이는 diff와의 관련도로 조절:
   - 변경된 동작: 정상 흐름 + 경계값(빈 값, 최대 길이, 잘못된 형식) + 오류 흐름(검증 메시지, 실패 응답 시 UI) + 상태 전이(로딩 → 완료, 활성/비활성).
   - 같은 화면의 나머지 동작: 정상 흐름 1회. 회귀는 대개 "안 건드린 줄 알았던 옆 기능"에서 난다.
   - 파일 업로드가 있으면 테스트 파일을 `$RUN_DIR/fixtures/`에 직접 만들어 쓴다(프로젝트에 이미 fixture가 있으면 그걸 우선). 파일이 없다고 업로드 시나리오를 건너뛰지 않는다. 먼저 코드(`accept` 속성, 검증 로직, 서버 설정)에서 허용 확장자·용량·개수 제한을 찾고, 그에 맞춰 준비한다:
     - 허용되는 정상 파일: 이미지면 진짜 PNG(1x1 PNG를 base64로 디코딩해 저장), 문서면 작은 txt/pdf
     - 허용되지 않는 확장자 파일(예: `.exe`, `.sh`)
     - 용량 제한보다 큰 파일: `node -e "require('fs').writeFileSync(process.argv[1], Buffer.alloc(N))" <경로>` (N = 제한 + 1KB)
     - 개수 제한이 있으면 제한 + 1개 분량의 정상 파일
     - 제한값을 코드에서 못 찾으면 정상 파일만 검증하고, 제한 검증은 리포트에 "미실행(제한값 불명)"으로 남긴다.
3. **판정 근거는 관찰 가능한 결과**다. 동작 후 `snapshot`/`find`로 기대한 변화(텍스트, 목록 개수, URL, 요소 상태)가 실제로 일어났는지 확인. "클릭이 에러 없이 끝남"은 통과가 아니다.
4. 동작마다 `console`(에러 레벨)과 `requests`를 확인. 콘솔 에러, 4xx/5xx 응답, 끝나지 않는 요청은 화면이 멀쩡해 보여도 실패 또는 경고로 기록.
5. **실패 처리**: 한 번 재시도해 재현되는지 확인(타이밍·애니메이션 탓인 오판 제거). 재현되면 `screenshot --filename="$RUN_DIR/<화면>-<동작>.png"`, 관련 콘솔/네트워크 응답 본문을 증거로 남기고, diff에서 의심 코드 위치(`file:line`)와 이유를 추정. 코드는 수정하지 않는다.
6. 의도된 변경인지 버그인지 애매하면(문구 변경, 레이아웃 이동 등) 실패가 아니라 "확인 필요"로 분류.

### 멈추고 묻는 경우

- 테스트 계정을 찾을 수 없음
- 되돌릴 수 없는 부작용이 있는 동작: 실제 결제, 외부 메일·SMS 발송, 공유/운영 DB 데이터 삭제. API가 localhost/mock/테스트 환경으로 향하는지 확인하고, 아니면 해당 동작은 건너뛰고 리포트에 "미실행(부작용)"으로 남기거나 묻는다. 로컬 DB에서의 생성·수정·삭제는 진행해도 된다.

## 4. 정리

`playwright-cli close`, 직접 띄운 dev 서버 종료. `$RUN_DIR`은 증거 보관용으로 남기고 경로를 리포트에 적는다. 프로젝트 안에 생긴 파일이 없는지 `git status`로 확인.

## 5. 리포트

대화에 아래 형식으로 출력한다:

```markdown
# e2e 회귀 진단 결과

범위: <diff 범위 또는 all> · 화면 N개 · 동작 M개
결과: ✅ 통과 a · ❌ 실패 b · ⚠️ 확인 필요 c · ⏭️ 미실행 d
증거 폴더: <RUN_DIR 절대경로>

## ❌ 실패
### 1. <화면> — <동작>
- 재현: 1) … 2) … 3) …
- 기대: …
- 실제: …
- 증거: <스크린샷 경로>, 콘솔 `…`, `POST /api/… 500`
- 원인 추정: `src/…/file.tsx:42` — <근거>

## ⚠️ 확인 필요
- <화면> — <내용> (의도된 변경인지 확인)

## ⏭️ 미실행
- <화면> — <동작>: <이유>

## ✅ 통과
| 화면 | 검증한 동작 |
|---|---|
| /cart | 수량 증감, 삭제, 빈 장바구니 표시, 결제 이동 |
```

실패를 먼저, 통과는 표로 압축. 무엇을 검증하지 **않았는지**를 숨기지 않는다 — 통과 목록만 보고 사용자가 커버리지를 과신하면 회귀를 놓친다.
