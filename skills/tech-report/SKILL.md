# 기술 보고 문서 작성

업무용 기술 보고 문서를 작성한다. 목표는 "읽는 사람이 최소 시간으로 판단에 필요한 정보를 얻는 문서".

## 핵심 원칙

1. **두괄식.** 결론·권고를 문서 맨 앞에 둔다. 보고 받는 사람은 바쁘고, 대부분 첫 화면만 읽는다. 첫 섹션만 읽어도 "무슨 일이고, 어떻게 하자는 것인지" 파악되어야 한다.
2. **근거는 수치로.** "크게 개선됨" 대신 "평균 응답 320ms → 45ms (86% 감소)". 사용자가 제공한 수치·날짜·고유명사는 하나도 빠뜨리거나 바꾸지 말고 그대로 보존한다. 수치가 틀린 보고서는 문서 전체의 신뢰를 무너뜨린다.
3. **독자에 맞춘 깊이.** 경영진·비기술 독자면 비용·효과·리스크 중심으로 쓰고 기술 세부는 뒤로. 기술 조직 내부면 구현 세부·대안 비교까지 본문에.
4. **과장·추측 금지.** 확인되지 않은 내용은 "추정", "검증 필요"라고 명시한다. 사용자가 주지 않은 수치나 사실을 지어내지 않는다.
5. **사실과 의견 분리.** 측정 결과·발생 사실(사실)과 권고·평가(의견)를 같은 문장에 섞지 않는다.

## 작성 전 확인

대화에서 다음을 추출한다:

- **독자**: 팀 내부 / 상위 조직 / 경영진 / 고객
- **목적**: 의사결정 요청 / 결과 공유 / 장애 소명 / 승인 요청
- **유형**: 아래 템플릿 중 무엇에 해당하는가

독자와 목적이 대화에 전혀 없으면 사용자에게 묻는다. 형식·분량 같은 부차적인 것은 기본값(Markdown, A4 1~2장)으로 진행하고, 적용한 가정은 문서가 아닌 답변에서 한 줄로 밝힌다.

## 유형별 구조

섹션 이름은 상황에 맞게 바꿔도 되지만 순서(결론 먼저)는 유지한다.

### 1. 기술 검토·선정 보고서 (대안 비교 후 권고)

```
# [제목: 무엇을 검토했고 결론이 뭔지 한 줄로]
## 요약 및 권고      ← 결론, 핵심 근거 2~3개, 권고 사항
## 검토 배경         ← 왜 검토했나, 요구사항·제약
## 대안 비교         ← 표로. 비교 축: 성능, 비용, 운영, 리스크
## 권고 근거         ← 왜 이 선택인가. 탈락 대안의 탈락 사유 포함
## 도입 시 고려사항  ← 리스크, 선행 작업
## 다음 단계
```

### 2. 장애(인시던트) 보고서

```
# [제목: 서비스명 + 날짜 + 장애 요지]
## 요약              ← 언제, 얼마나, 무엇이, 영향 규모, 현재 상태
## 영향 범위         ← 영향 받은 사용자/건수/금액, 지속 시간
## 타임라인          ← 시각별 발생→탐지→대응→복구. 시각 모두 명시
## 원인 분석         ← 직접 원인과 근본 원인 구분
## 조치 내용         ← 이미 수행한 긴급 조치
## 재발 방지 대책    ← 항목별 담당·기한이 있으면 명시
```

장애 보고서는 소명 문서다. 방어적 표현("불가피했음")을 피하고 사실을 시각과 함께 담담하게 기술한다.

### 3. 성능 개선·기술 결과 보고서

```
# [제목]
## 요약              ← 무엇을 했고 결과가 어떤지 수치로
## 배경 및 목표      ← 개선 전 상태, 목표치
## 수행 내용
## 결과              ← 전/후 비교 표 또는 수치. 측정 조건 명시
## 한계 및 향후 과제
```

### 4. 기술 도입 제안서 (승인 요청)

검토 보고서 구조에 **비용**(도입·운영 비용, 인력)과 **일정** 섹션을 추가한다. 승인권자가 판단할 재료(비용 대비 효과)가 요약에 들어가야 한다.

## 문체 규칙

- **종결 형식**: 요약·표·불릿은 개조식("~함", "~필요", 명사형 종결), 배경 설명 문단은 서술식 가능. 같은 문서 안에서 같은 레벨은 같은 형식으로 통일한다.
- **수치 표기**: 단위 명시, 천 단위 콤마(1,200건), 변화는 "전 → 후 (증감률)" 형태.
- **용어 일관**: 같은 대상은 문서 전체에서 하나의 명칭만. 통용되는 영문 기술 용어(Redis, TTL, rollback)는 억지로 번역하지 않는다.
- **비교는 표로**: 대안이 2개 이상이면 표. 행은 비교 축(성능/비용/운영/리스크), 열은 대안.
- **날짜·시각**: "어제", "최근" 같은 상대 표현은 절대 날짜·시각으로 변환한다(예: 2026-11-12(수) 02:00).

## 제출 전 체크리스트

작성 후 스스로 검증한다:

- [ ] 첫 섹션만 읽어도 결론과 요청 사항이 파악되는가
- [ ] 사용자가 준 수치·날짜·사실이 전부, 정확히 들어갔는가
- [ ] 지어낸 수치·사실이 없는가 (추정은 추정이라 표시했는가)
- [ ] 비교 대상이 있으면 표로 정리했는가
- [ ] 독자가 다음에 뭘 해야 하는지(의사결정/승인/확인) 명확한가
