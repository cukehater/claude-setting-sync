# squash-commit-range

이미 만들어진 커밋들을 합쳐 히스토리를 읽기 좋게 만든다. 히스토리 재작성이라 되돌리기가 번거로우므로, **계획을 먼저 보여주고 승인을 받은 뒤에만** 실행한다.

## 이 스킬이 하는 일과 하지 않는 일

**한다:** 인접한 커밋을 묶어 개수를 줄인다. 최종 트리(코드 내용)는 한 글자도 바뀌지 않는다.

**하지 않는다:** 커밋 순서를 바꾸지 않는다. 파일 기준으로 보면 연관돼 보여도 멀리 떨어진 커밋은 따로 남는다. 순서를 바꾸려면 재적용 과정에서 충돌이 날 수 있고, 충돌을 기계적으로 푸는 순간 "트리가 안 바뀐다"는 이 스킬의 유일한 안전 보장이 깨진다. 재배치가 꼭 필요하면 그 사실을 사용자에게 말하고 손으로 하게 둔다.

**하지 않는다:** `git push`. force-push가 필요한 상황이면 무엇을 밀어야 하는지 알려주고 사용자가 직접 하게 한다.

## 1단계: 범위 확정

사용자가 준 범위를 `<base>..<head>` 형태로 만든다. `<base>`는 **합치지 않고 그대로 둘 마지막 커밋**이다(범위에 포함되지 않는다).

자주 나오는 표현과 대응:
- "마지막 3개" → `HEAD~3..HEAD`
- "이 브랜치에서 한 작업 전부" → `git merge-base <기준브랜치> HEAD`의 결과를 base로
- "abc123부터" → `abc123^..HEAD` (abc123 자신도 합칠 대상이면 `^`가 필요하다)
- 범위를 안 줬으면 `git log --oneline -20`을 보여주고 어디까지인지 물어본다

범위가 모호한 채로 진행하지 않는다. 잘못된 base는 남의 커밋까지 말아먹는다.

## 2단계: 안전 점검

실행 전에 전부 확인한다. 하나라도 걸리면 멈추고 사용자에게 알린다.

```bash
git status --porcelain              # 비어 있어야 한다
git rev-parse --abbrev-ref HEAD     # 현재 브랜치
git log --oneline <base>..HEAD      # 대상 커밋
```

- **워킹트리가 더럽다** → 멈춘다. `reset --hard`를 쓰므로 커밋 안 된 변경이 사라진다. 커밋하거나 stash하라고 안내한다.
- **rebase/merge/cherry-pick 진행 중** (`.git/rebase-merge`, `.git/MERGE_HEAD` 존재) → 멈춘다.
- **base가 HEAD의 조상이 아니다** (`git merge-base --is-ancestor <base> HEAD` 실패) → 범위가 잘못됐다. 멈춘다.
- **범위에 머지 커밋이 있다** → 3단계 스크립트가 막아 준다. 합치면 병합 구조가 조용히 평탄화되기 때문이다.

### 이미 푸시된 커밋이 범위에 있으면

```bash
git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null
git rev-list --count <base>..@{u} 2>/dev/null   # 0보다 크면 푸시된 커밋이 범위에 있다
```

푸시된 커밋이 끼어 있으면 **그냥 진행하지 말고 경고부터 한다.** 다른 사람이 이미 그 커밋 위에 작업하고 있을 수 있고, 히스토리를 갈면 그쪽에서 충돌이 난다.

경고에 반드시 담을 것: 어느 원격 브랜치인지, 몇 개 커밋이 다시 쓰이는지, 반영하려면 `git push --force-with-lease`가 필요하다는 사실, 그리고 그건 사용자가 직접 해야 한다는 것.

사용자가 명시적으로 확인해 주면 진행한다. "알아서 해"나 침묵은 확인이 아니다.

## 3단계: 그룹 계산

```bash
bash "<SKILL_DIR>/scripts/group-commits.sh" <base>..HEAD
```

`<SKILL_DIR>`는 이 스킬이 로드될 때 제시되는 base directory 절대경로다. 프로젝트 상대경로(`.claude/skills/...`)로 부르면 안 된다 — 이 스킬은 유저 레벨(`~/.claude/skills/`)에 설치되어 있어 대상 레포에는 스크립트가 없다.

인접한 커밋을 훑으면서 파일 집합이 겹치면 같은 그룹으로 묶는다. 겹침은 전이적이다 — `c1(A)`, `c2(A,B)`, `c3(B)`는 c1과 c3이 직접 안 겹쳐도 한 그룹이 된다.

출력은 그룹마다 `GROUP<n>` / `COMMIT` 줄들 / `LAST`(그 그룹 마지막 커밋의 전체 SHA) / `FILES` 순이다. `LAST` 값이 5단계에서 그대로 쓰인다.

스크립트 결과는 출발점이지 정답이 아니다. 아래 경우엔 손으로 조정하고, **왜 조정했는지 계획에 적는다**:
- 사용자가 "전부 하나로"라고 했다 → 그룹 수와 무관하게 전체를 한 그룹으로 본다(그래도 4단계 승인은 받는다).
- 한 그룹이 명백히 서로 다른 두 작업인데 공용 파일(설정, 배럴 파일, 타입 정의) 하나 때문에 붙었다 → 쪼개는 게 나은지 사용자에게 묻는다.
- 그룹이 커밋 하나짜리다 → 합칠 게 없으니 메시지도 그대로 둔다. 굳이 손대지 않는다.

## 4단계: 계획 제시 — 여기서 멈춘다

실행 전에 이 형식으로 보여주고 승인을 기다린다.

```
커밋 N개 → M개

[그룹 1] 3개 → 1개
  a1b2c3d feat(rop): 로그인 폼 추가
  e4f5g6h fix(rop): 로그인 폼 유효성 검사 누락 처리
  i7j8k9l style(rop): 로그인 폼 간격 조정
  파일: apps/rop/modules/auth/LoginForm.tsx, apps/rop/modules/auth/schema.ts
  새 메시지: feat(rop): 로그인 폼 추가

[그룹 2] 1개 → 1개 (그대로)
  m0n1o2p chore: prettier 설정 갱신

푸시 상태: 로컬 전용 (force-push 불필요)
백업: 실행 전 squash-backup-<타임스탬프> 브랜치를 만든다
```

새 커밋 메시지는 `git-commit` 스킬 규칙을 따른다: `type(scope): 설명` 한 줄 — 설명 언어는 그 레포 히스토리의 지배 언어를 따른다. 본문 없음, 마침표 없음, 워터마크/트레일러 없음. 그룹 안에서 타입이 섞이면(`feat` + `fix` + `style`) 그 작업의 **본질**을 고른다 — 새 기능을 만들다가 중간에 자기 버그를 고친 것이면 전체는 `feat`다. 메시지는 "무엇을 했는가"를 말해야지 "무엇을 합쳤는가"를 말하면 안 된다. `feat: 로그인 폼 추가 및 수정 3건 반영` 같은 문장은 합치기 전보다 정보가 적다.

사용자가 그룹이나 메시지를 고치자고 하면 반영하고 다시 보여준다.

## 5단계: 실행

승인을 받은 뒤에만. 먼저 되돌아갈 지점을 만들고, **그 지점이 실제로 생겼는지 확인한다.** 뒤따르는 복구 절차가 전부 이 백업에 의존하므로, 만들었다고 가정하면 안전장치가 자기 자신을 검증하지 않는 꼴이 된다.

```bash
ORIG=$(git rev-parse HEAD)
BACKUP="squash-backup-$(date +%Y%m%d-%H%M%S)"
git branch "$BACKUP"
git rev-parse --verify "$BACKUP^{commit}" >/dev/null   # 실패하면 여기서 멈춘다
```

그다음 그룹을 오래된 순서대로 하나씩 쌓는다. 그룹의 `LAST` SHA와 승인된 메시지를 쓴다. **커밋할 때마다 새 SHA를 그룹의 `LAST`와 짝지어 적어 둔다** — 6단계에서 경계마다 스냅샷을 대조하는 데 쓴다.

```bash
git branch -f _squash_tmp <base>
PAIRS=""

# 그룹마다 반복 (오래된 것부터):
git reset --hard <그룹의 LAST SHA>
git reset --soft _squash_tmp
git commit -m "<승인된 메시지>"
PAIRS="$PAIRS $(git rev-parse HEAD):<그룹의 LAST SHA>"
git branch -f _squash_tmp HEAD

git branch -D _squash_tmp
```

범위가 HEAD에서 끝나지 않으면(중간 구간을 합치는 경우) 범위 뒤의 커밋들도 같은 방식으로 하나씩 재적용한다 — 각각을 1개짜리 그룹으로 보고 원래 메시지를 그대로 쓰면 된다. 트리를 그대로 옮기므로 충돌은 나지 않지만, **그 커밋들의 SHA도 전부 바뀐다.** 4단계 계획에 몇 개가 그렇게 되는지 반드시 적는다.

`reset --hard`가 워킹트리를 그 커밋 상태로 옮기고, `reset --soft`가 브랜치 포인터만 그룹 시작점으로 되돌린다. 남은 차이가 통째로 스테이징된 상태가 되므로 커밋 하나로 떨어진다. 파일 삭제와 이름 변경도 트리 단위로 따라온다 — `checkout <sha> -- .` 방식은 삭제를 놓치므로 쓰지 않는다.

## 6단계: 검증 — 이게 이 스킬의 안전장치다

```bash
bash "<SKILL_DIR>/scripts/verify-squash.sh" "$ORIG" "$BACKUP" $PAIRS
```

**종료 코드가 0이어야 한다.** 스크립트가 다섯 가지를 본다: 백업이 살아 있는가, 백업이 정말 `ORIG`를 가리키는가, 최종 트리가 원본과 같은가, 그룹 경계마다 스냅샷이 원본과 같은가, 워킹트리가 깨끗한가.

비교는 `git diff`가 아니라 **트리 해시**(`git rev-parse <커밋>^{tree}`)로 한다. 이유가 있다:

- `git diff`는 **차이가 있어도 종료 코드가 0이다.** 눈으로 "출력이 비었네" 확인하는 방식이라 자동 판정에 쓸 수 없고, 출력을 흘려보내면 실패를 통과로 착각한다. 사람이 읽을 요약이 필요하면 `git diff --exit-code --stat "$ORIG" HEAD`처럼 `--exit-code`를 붙여야 한다.
- 트리 SHA는 모든 경로·파일 모드·blob 내용에 대한 Merkle 해시다. 같으면 바이트 단위로 같다. diff 관련 git 설정에도 영향받지 않는다.
- 최종 HEAD만 보면 중간이 어긋나도 통과한다. 경계마다 대조해야 히스토리의 각 시점이 원본과 같다고 말할 수 있다.

**실패하면 추측해서 고치지 말고 즉시 되돌린다.** 스크립트가 복구 명령을 그대로 출력한다:

```bash
git reset --hard "$BACKUP"
```

백업까지 없다고 나오면 `git reflog`에서 `$ORIG`를 찾아 `git branch squash-backup-recovered $ORIG`로 먼저 고정한 뒤 되돌린다. 그리고 무엇이 어긋났는지 사용자에게 그대로 보여준다.

검증이 통과하면 결과를 보고한다:

```bash
git log --oneline <base>..HEAD
```

- 백업 브랜치 이름을 알려주고, 확인 끝나면 `git branch -D <백업>`으로 지우면 된다고 안내한다. 지우는 건 사용자 몫이다.
- 푸시된 커밋이 섞여 있었다면 `git push --force-with-lease` 명령을 그대로 적어 주되, 실행은 사용자가 한다. `--force`가 아니라 `--force-with-lease`인 이유는 그 사이 원격이 움직였으면 거부돼서 남의 커밋을 덮어쓰는 사고를 막아 주기 때문이다.

## 예시

**예시 1 — 리뷰 수정 커밋 흡수**

입력: "리뷰 받고 고친 커밋들 원래 커밋에 넣어줘, HEAD~4부터"

`HEAD~4..HEAD`를 계산하니 4개가 전부 같은 컴포넌트 파일을 건드려 한 그룹. 계획을 보여주고 승인받아 `feat(rop): 자녀 정보 카드 추가` 하나로 합친다. `git diff` 비어 있음 확인, 백업 브랜치 안내.

**예시 2 — 섞인 범위**

입력: "이 브랜치 커밋 정리해줘"

`git merge-base develop HEAD`로 base를 잡으니 9개. 그룹은 3개로 나뉘고, 그중 하나는 커밋 1개짜리(설정 파일 단독 변경)라 그대로 둔다. 9개 → 3개 계획을 제시.

**예시 3 — 푸시된 범위**

입력: "마지막 5개 합쳐줘"

`git rev-list --count <base>..@{u}`가 3을 반환 — 5개 중 3개가 이미 `origin/feature/x`에 있다. 계획을 보여주기 전에 먼저 경고하고, 사용자가 명시적으로 확인한 뒤에 진행한다. 완료 후 force-push 명령을 안내하되 직접 실행하지 않는다.
