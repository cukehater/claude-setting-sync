# Prompt Forge

사용자는 머릿속 요구를 다듬지 않고 던진다. 이걸 그대로 AI에게 넘기면 AI는 빈칸을 자기 마음대로 채우고, 결과는 "말한 대로지만 원한 건 아닌" 것이 된다. 할 일은 **빈칸을 AI 대신 사용자가 채우게 만드는 것**이다. 결정이 필요한 지점과 터질 문제를 먼저 찾아내 묻고, 답을 받아 모호함 없는 프롬프트로 정리한다.

**이 스킬은 작업을 구현하지 않는다.** 결과물은 프롬프트 하나다. 사용자가 실행을 원하면 그때 따로 한다.

## 진행 순서

### 1. 의도 파악

원문에서 다음을 뽑는다.
- **진짜 목표**: 요청한 *방법*이 아니라 그 방법으로 얻으려는 *결과*. "캐시 붙여줘"의 목표는 대개 "응답 느린 거 해결"이다. 목표가 방법과 어긋나 보이면 질문 대상이다.
- **명시된 요구와 제약**
- **암묵적 기대**: 말은 안 했지만 당연히 원할 것(기존 기능 안 깨기, 기존 코드 스타일 따르기 등)

파악한 목표를 한 줄로 요약해 첫 질문 묶음 앞에 보여준다. 여기서 틀렸으면 사용자가 바로 바로잡을 수 있다.

### 2. 코드 탐색 (git repo 안일 때)

질문하기 전에 코드에서 알 수 있는 건 직접 확인한다. 사용자에게 "프레임워크가 뭐예요?"라고 묻는 건 사용자의 시간을 낭비하는 것이다.

- 스택, 버전, 디렉터리 구조
- 요청과 관련된 파일·함수·컴포넌트, 그걸 호출하는 쪽
- 비슷한 기능이 이미 있는지, 있다면 어떤 패턴인지
- 테스트 구조와 실행 방법, lint·타입체크 명령
- 커밋 컨벤션이나 CLAUDE.md 같은 프로젝트 규칙

탐색은 요청과 관련된 범위까지만 한다. 전체 코드베이스를 훑을 필요는 없다. 찾은 사실은 프롬프트에 **파일 경로와 함께** 넣는다. 그래야 실행하는 AI가 같은 탐색을 반복하지 않는다. repo가 아니면 이 단계를 건너뛰고 스택 같은 기본 정보도 질문 목록에 넣는다.

### 3. 빈칸과 위험 찾기

`references/checklist.md`의 점검 항목을 요청에 대입한다. 모든 항목을 기계적으로 묻는 게 아니라, **답에 따라 구현이 실제로 달라지는 것**만 골라낸다.

찾은 것을 세 가지로 분류한다.
- **결정 필요**: 선택지가 여럿이고 사용자 의도에 따라 갈리는 것. 질문한다.
- **관례로 해결**: 업계 표준이나 기존 코드 패턴으로 답이 정해지는 것. 묻지 않고 기본값으로 정한 뒤 프롬프트의 "가정"에 적는다.
- **예상 문제**: 구현하면 터질 수 있는 것(기존 데이터와 충돌, 하위 호환 깨짐, 동시성, 성능, 보안). 대응 방향이 여럿이면 질문하고, 하나뿐이면 프롬프트에 대응을 명시한다.

### 4. 집요한 인터뷰

결정 필요 항목을 AskUserQuestion으로 묻는다.

- **영향 큰 것부터.** 답에 따라 다른 질문이 사라지거나 생기는 것(범위, 접근 방식)을 먼저 묻는다. 세부 사항은 뒤로.
- **한 번에 최대 4개.** 넘으면 다음 차례로 넘긴다.
- **선택지와 추천을 준다.** "어떻게 할까요?" 대신 구체적인 선택지 2~4개와 각각의 결과를 보여주고, 추천안을 첫 번째에 둔다. 사용자는 고르기만 하면 된다.
- **질문에 근거를 넣는다.** 코드에서 찾은 사실 때문에 생긴 질문이면 그 사실을 질문 안에 적는다. ("`orders` 테이블에 기존 행이 12만 건 있습니다. 새 컬럼 기본값은?")

답을 받으면 **그 답이 새로 만든 빈칸**을 다시 찾는다. "소프트 삭제로 할게요"라는 답은 "삭제된 항목이 목록 조회·검색·유니크 제약에서 어떻게 처리되나?"라는 새 질문을 낳는다. 이걸 놓치지 않는 것이 이 스킬의 핵심이다. 사용자가 대충 답했거나 답이 다른 답과 충돌하면 그것도 짚는다.

**멈출 때:**
- 남은 빈칸이 전부 "관례로 해결"이다.
- 사용자가 "나머지는 알아서", "그냥 만들어"라고 한다. 남은 항목은 추천안으로 정하고 "가정"에 적는다.
- 같은 주제로 세 차례 넘게 왔다 갔다 한다. 쟁점을 정리해 보여주고 결정을 요청한다.

### 5. 프롬프트 생성

`references/template.md`의 구조로 한국어 프롬프트를 쓰고, 복사하기 쉽게 코드블록 하나에 담아 출력한다. 코드블록 밖에는 짧게 두 가지만 덧붙인다.
- 사용자가 직접 정하지 않고 기본값으로 정한 가정 목록 (바꾸고 싶으면 말하라고)
- 프롬프트 길이가 길면 핵심 결정 3줄 요약

## 프롬프트 작성 원칙

- **검증할 수 없는 말은 쓰지 않는다.** "적절히", "깔끔하게", "잘", "필요하면", "등" 같은 말은 실행하는 AI에게 판단을 떠넘긴다. 구체적인 조건, 값, 동작으로 바꾼다. "에러 처리 잘 해줘" 대신 "API가 4xx를 반환하면 응답의 `message`를 토스트로 표시하고, 5xx·네트워크 오류면 '잠시 후 다시 시도해 주세요'를 표시한다."
- **사실을 만들어내지 않는다.** 확인하지 않은 파일 경로, 함수 이름, 버전은 쓰지 않는다. 코드에서 확인한 것만 경로와 함께 쓰고, 모르는 건 "실행 시 확인할 것"으로 표시한다.
- **이유를 함께 쓴다.** 결정 사항마다 왜 그렇게 정했는지 한 줄 붙인다. 실행하는 AI가 예상 못 한 상황을 만나도 의도에 맞게 판단할 수 있다.
- **범위 밖을 명시한다.** 하지 말아야 할 것(건드리지 말 파일, 이번에 안 할 기능)을 적어야 AI가 "하는 김에" 리팩터링하지 않는다.
- **완료 기준은 실행 가능하게.** "테스트 통과"가 아니라 어떤 명령으로 무엇을 확인하는지 적는다.
- **멈출 지점을 정한다.** 실행 중에 사용자 확인이 필요한 상황(스키마 변경, 파일 삭제, 예상과 다른 코드 구조 발견)을 적어둔다.
- **대화 과정은 넣지 않는다.** 프롬프트는 결론만 담는다. "사용자가 처음엔 A라고 했다가 B로 바꿨다" 같은 경위는 필요 없다.
- **분량은 작업 크기에 맞춘다.** 한 줄 수정에 템플릿 전 섹션을 채우지 않는다. 해당 없는 섹션은 뺀다.

## 예시

**원문:** "로그인 유지 기능 넣어줘 자동로그인 그거"

**탐색 결과 (예):** Next.js App Router, `src/lib/auth.ts`에서 JWT를 메모리에만 저장, refresh token 없음.

**첫 질문 묶음 (예):**
> 목표: 브라우저를 닫았다 열어도 로그인 상태가 유지되게 한다.
> 1. 유지 기간은? (7일 추천 / 30일 / 사용자가 체크박스로 선택)
> 2. 현재 `src/lib/auth.ts`는 access token을 메모리에만 저장하고 refresh token이 없습니다. 방식은? (httpOnly 쿠키 + refresh token 추천 / localStorage에 access token)
> 3. 백엔드 refresh 엔드포인트가 필요합니다. 백엔드도 이번 작업 범위인가요?

답에 따라 다음 차례에서 "다른 기기에서 로그아웃하면 모든 세션 무효화?", "refresh 실패 시 동작은?" 같은 질문으로 이어진다.
