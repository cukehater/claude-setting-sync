# 빈칸·위험 점검 항목

요청에 대입해 **답에 따라 구현이 달라지는 항목만** 고른다. 전부 묻지 않는다.

## 범위
- 이번에 할 것과 안 할 것의 경계. 연관 기능(관리자 화면, 모바일, 다국어)까지 포함인가?
- 프론트만인가, 백엔드·DB·인프라까지인가?
- 기존 코드를 고치는가, 새로 만드는가? 기존 것을 대체한다면 옛 것은 지우는가?

## 동작 명세
- 정상 흐름: 입력, 처리, 출력이 구체적으로 무엇인가?
- 트리거: 누가, 언제, 무엇으로 실행하는가? (사용자 클릭, 스케줄, 이벤트)
- 권한: 누가 할 수 있고 누가 못 하는가?
- 상태: 로딩, 빈 상태, 오류, 부분 성공일 때 각각 어떻게 보이나?

## 엣지 케이스
- 입력이 비었거나, 너무 크거나, 형식이 틀리거나, 중복일 때
- 동시에 두 번 실행될 때 (더블클릭, 동시 요청, 경쟁 상태)
- 네트워크 끊김, 타임아웃, 외부 서비스 장애
- 중간에 실패했을 때: 롤백하는가, 부분 결과를 남기는가, 재시도하는가?

## 데이터
- 기존 데이터는 어떻게 되는가? 마이그레이션이 필요한가? 기본값은?
- 삭제는 실제 삭제인가, 소프트 삭제인가? 연관 데이터는?
- 하위 호환: 기존 API 소비자, 저장된 데이터, 구버전 클라이언트가 깨지지 않는가?

## 기존 코드와의 관계
- 비슷한 기능이나 공용 유틸이 이미 있는가? 재사용인가, 별도 구현인가?
- 이 변경이 다른 호출부에 영향을 주는가?
- 따라야 할 기존 패턴(상태관리, 에러 처리, 네이밍)이 있는가?

## 비기능
- 성능: 데이터 규모, 응답 시간 기대치, 페이지네이션 필요 여부
- 보안: 입력 검증, 인증·인가, 민감정보 노출, 로그에 남기면 안 되는 것
- 접근성, 반응형, 브라우저 지원 (UI 작업일 때)

## 기술 선택
- 새 라이브러리를 추가해도 되는가, 기존 의존성만 쓰는가?
- 접근 방식이 여럿이면(서버/클라이언트, 동기/비동기, 폴링/웹소켓) 어느 쪽인가?

## 검증
- 완료를 무엇으로 확인하는가? (테스트 명령, 수동 확인 시나리오, 타입체크)
- 테스트를 새로 써야 하는가? 어떤 수준(단위, 통합, e2e)?

## 진행 방식
- 실행 중 사용자 확인이 필요한 지점 (스키마 변경, 파일 삭제, 대규모 변경)
- 커밋 단위, 브랜치, PR 여부

## 목표 자체
- 요청한 방법이 진짜 목표를 이루는 최선인가? 더 단순한 방법이 있다면 그것도 선택지로 제시한다.
- 요청끼리 충돌하지 않는가?
